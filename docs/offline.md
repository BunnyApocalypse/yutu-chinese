# Offline use and deployment

The owner chose (2026-10-13): all stroke data saved on the device, and automatic deployment.

## The two copies

- **Two copies at one site** (the owner, 2026-10-13), **at https://yutuchinese.com since 2026-11-10** (the move, below): built from their branches, after `npm test` on each (not the browser tests), and published, **during the move**, by `BunnyApocalypse/yutuchinese-site` (`site-repo/deploy.yml`), started by hand; this repository's `.github/workflows/deploy.yml` meanwhile publishes the moving page at the old address, only on a push to `main` changing a file it is built from (`paths`: its own files, and `src/db.js`, `backup.js`, `syncCode.js`, `style.css`, the texts, the packages; the owner, 2026-11-10, since every other run sent the same page again and risked a hung Pages; a new import in `src/move.js` is added there). Before the move, and again after it (phase 3), this repository's workflow builds and publishes both. In phase 3 a push to `main` changing only `docs/` or Markdown files starts nothing again (`paths-ignore`, 2026-11-10): each run sends the whole site again. Pages usually puts the files in place (about 350 MB uploaded) in under a minute, but now and then hangs at "syncing_files" until `deploy-pages` gives up after 10 minutes ("Timeout reached"; it allows no longer): start a fresh run. On 2026-11-10 it hung four times in a row, with no incident on GitHub's status page.
  - **stable**, from the `stable` branch, at https://yutuchinese.com/app/ (before the move `https://bunnyapocalypse.github.io/yutu-chinese/`): what people use, the owner's data included;
  - **test**, from `main`, at `/app/test/`.
- **To release** (ask the owner first): the entry at the top of `src/changes.js`, then `git push origin main:stable`, `git push origin main`, and during the move `gh workflow run deploy.yml -R BunnyApocalypse/yutuchinese-site`. (Before the move one run of this repository's workflow, started by the push to `main`, published both copies; two runs at once had competed and timed out, 2026-11-10.) The push to `stable` starts nothing by itself: the `github-pages` environment only lets `main` publish (a run from `stable` is refused, "not allowed to deploy due to environment protection rules"). If it fails with "Fetching artifact metadata failed", start a fresh run; a re-run uploads a second copy and fails.
- **The test copy is told apart by `VITE_CHANNEL=test`** (`__CHANNEL__`, `vite.config.js`). A browser keeps one set of databases and caches for the whole site, so the test copy has its own database (`hanzi-trainer-test`, `src/db.js`) and app-file store (`test-app-…`), and the stable service worker leaves `test/` alone. It says "(test)" in its title, version line and home-screen name, and has no recording packs (to stay under GitHub's 1 GB; the two copies are about 565 MB). **Anything else kept per site must be kept apart the same way.**
- **The build is relative** (`base: './'`), so `dist/` works in any folder; build addresses with `import.meta.env.BASE_URL`, never a leading `/`.

## The service worker and offline data

- **`src/serviceWorker.js`** is copied by `scripts/build-offline.js` (`postbuild`) to `dist/sw.js` with `VERSION` (a fingerprint of the app's files) and `APP_FILES` in front. It answers from the device's caches if it can, the network otherwise. None under `npm run dev`.
- **The recordings of "Basics of Chinese" are app files** (`BASICS_RECORDINGS` in `src/basicsSounds.js`, 11 small files; 2026-10-21), so that page plays offline from the start; every other recording is kept once played or saved from Settings.
- **Two caches:** `app-<VERSION>`, replaced each version; `offline-data` (stroke data, dictionary, word lists, notes), kept across versions. Recordings have their own store (`docs/word-page.md`).
- **Stroke data is saved in the background, in packs**: 10,600 files one by one is too slow for a phone, so they are packed 600 to a file into `dist/offline/` (18 packs, 35 MB; about 14 MB downloaded), listed in `offline/index.json`. `saveOfflineData` in `src/offline.js` puts every file into the cache under its own address, so `loadCharData` and the service worker know nothing of packs. A pack's name carries a fingerprint and a finished pack leaves a mark, so an interrupted download resumes and unchanged packs aren't fetched again. The single files stay in `dist/` until the packs are in.
- **A new version waits** for "New version ready: tap to reload" in the footer, so the app never changes under a review; without the tap it takes over once every window of the app is closed.
- **Long-term storage** (`navigator.storage.persist()`) is asked for in the introduction or from Settings, never by itself (`docs/interface.md`); Settings shows how it stands under "Offline use", with the download's progress.
- **`tests/browser/offline.browser.js`** builds the app, serves `dist/` from a sub-folder with a plain file server (`startBuiltApp`, like GitHub Pages), waits for everything to be saved, fakes a new version, stops the server and checks writing, the dictionary and tone cards. It leaves `dist/` built.
- **Not tested here:** installing on a real phone, and airplane mode on it.

## The old address

The repository was renamed from `hanzi-trainer` to `yutu-chinese` on 2026-10-15, moving the site. GitHub forwards a renamed repository's code and remotes but not its Pages site, so:

- **Words and progress came along by themselves** (data is kept per site, not per folder); possibly not in an app on an iPhone's home screen, untested.
- **A new repository `BunnyApocalypse/hanzi-trainer`** publishes only `redirect/` (see its README): a page, also as `404.html`, sending any address under `/hanzi-trainer/` to the same place under `/yutu-chinese/`, and a `sw.js` (also `test/sw.js`) that replaces the old service workers, removes itself and sends open windows on, since an installed copy never asks for the page but does check `sw.js`. Because that repository exists, GitHub no longer forwards the old name: remotes must point to `yutu-chinese`.
- **`forgetOldFolder` in `src/offline.js`** deletes once (`old-folder-forgotten` in `localStorage`) the service workers and saved data under `/hanzi-trainer/` (about 45 MB), never while served from there. Tested in `tests/browser/offline.browser.js`.

## The move to yutuchinese.com

**Decided by the owner (2026-11-10):** the app moves to its own domain, `yutuchinese.com` (bought on Namecheap, DNS at Cloudflare), still on GitHub Pages: the stable copy at `https://yutuchinese.com/app/`, the test copy at `/app/test/` (the same layout as `/yutu-chinese/` and `/yutu-chinese/test/`, so the service worker and packs work unchanged). The site's root is kept for a page about the app, to come later; until then it forwards to `/app/` (later it can send someone who already uses the app straight in, as Skritter does: same site, so it can tell). `www` forwards to the bare domain (GitHub does it). The old address shows a moving page only, never the old app beside the new one (two copies to study in would drift apart). Code and site stay in one repository, this one, without a rename (the owner, 2026-11-10, over renaming it and giving the old name to a repository for the moving page): for the time of the move a temporary repository publishes the app at the new address (`site-repo/`), and this one the moving page at the old; then this one publishes at the new address itself (the phases below). `hanzi-trainer` is deleted then too.

**Why a moving page:** a browser keeps data per site (`bunnyapocalypse.github.io` and `yutuchinese.com` are two), so learners' words stay at the old address until handed over; only a page there can read them. GitHub's own forwarding for a custom domain would send people away from them.

**The moving page** (`move.html`, `src/move.js`; built by `npm run build:move` with `vite.move.config.js` and `scripts/finish-move.js` into `dist-move/`, the test copy's with `VITE_CHANNEL=test` into `dist-move/test/`; about 1 MB, no stroke data or recordings): it opens the database with the app's own `db.js` (bringing an old one up to date) and, with no words or reviews, sends the visitor to the new address at once. Otherwise it says how many words and reviews are there and offers:

- **"Move my words"** (`moveByWindow`): opens `<new address>#move-in` in a window, in the tap itself (a window opened later is blocked), and hands over with `postMessage`: the new window says `yutu-move-ready`, this one sends `yutu-move-data` (`buildBackup()`, the sync store and outbox from `readSyncState()` in `db.js`, and the language chosen, `savedLanguage()` in `text.js`), the new one reports its saving in parts (`yutu-move-progress`, shown here as "Saving at yutuchinese.com: {saved} of {total} records"; the owner, 2026-11-10, after a slow move of their own history) and answers `yutu-move-done` or `yutu-move-failed`. A minute without a word from it ends the wait ("didn't answer"), each word starting the minute again. Each side listens only to the other's site and window. The move is noted in `localStorage` (`moved-at`, `moved-at-test`), so a second visit says when; moving again combines.
- **In an installed app** (`display-mode: standalone`, not an iPhone's Home Screen): no button, but the page's address with "Copy the address" and the steps: open it in the browser, which has the same words, move from there, then install the app from the new address and remove this one (`move-installed`, `move.installedText`). Found on the owner's tablet (2026-11-10): the window the button opened from Firefox's installed web app had no way back ("this window can't reach the page"); the same page in Firefox itself moved everything.
- **On an iPhone's or iPad's Home Screen** (`navigator.standalone`), where a window opens in Safari, which keeps its words apart: the steps to add the new address to the Home Screen and join with the sync code (shown, with a link) if the device syncs, else with a backup file; then remove the old app.
- **A backup file**, always.

Nothing is deleted at the old address. Its service worker (`src/moveServiceWorker.js`, published as `sw.js`) replaces the app's: an installed app never asks for the page but does check `sw.js`, so it gets this one, which removes itself and reloads open windows onto the moving page. Caches are left (about 50 MB of stroke data and recordings a device; not yet cleaned up).

**The app taking the words in** (`src/moveIn.js`, before `startUp()` in `main.js`): opened with `#move-in` by a window at `__MOVE_FROM__` (`VITE_MOVE_FROM`; in a build `https://bunnyapocalypse.github.io`), it takes the address's `#move-in` out, waits up to a minute for the words under "Loading…" (opened without a window to answer to, `window.opener` empty, it says so instead, with the backup file, and starts nothing: the app would otherwise greet a learner who has words with the introduction; a reload opens it as usual), checks them (`checkBackup`), restores them (`restoreBackup`, saying how far as Import backup does, `import.saving`) or, if words are there already, combines (`mergeBackups`, as Import backup's Combine), puts the syncing records in place unless this address syncs already (`replaceSyncState`; then `sendEverything` if combined), saves the language (`saveLanguage`), answers, and reloads. Syncing so goes on where the old address stopped, unsent changes included, with the same device in the sync. The introduction is not shown: `welcomeDone` came with the settings.

**Tested** in `tests/browser/move.browser.js` (two dev servers, `localhost:5294` as the old address and `127.0.0.1:5293` as the new: a browser keeps two host names apart): no words, sent on at once; opened with `#move-in` and no window behind it, says so and starts on reload; 109 words, the progress shown at the old address, the language and a sync code handed over, kept at the old address, no introduction; in an installed app (`matchMedia` answered "standalone" before the page's scripts run: headless Chromium ignores `display-mode` in `Emulation.setEmulatedMedia`, and `Page.addScriptToEvaluateOnNewDocument` needs `Page.enable`), the browser steps and no button. It failed with the receiving side switched off, and caught the language saved after "done" (now before); the test of no window behind fails with the earlier `openedToMoveIn`.


**In three phases:**

1. **Trying the new address** (from 2026-11-10): `BunnyApocalypse/yutuchinese-site` (`site-repo/`: its README and workflow; Pages from Actions, custom domain `yutuchinese.com`) builds this repository's `stable` into `app/` and `main` into `app/test/`, with a page forwarding to `app/` at the top, and publishes them at `yutuchinese.com`; started by hand, `gh workflow run deploy.yml -R BunnyApocalypse/yutuchinese-site`. The old address is unchanged. The owner tries the new one (installing it, joining with the sync code).
2. **The move:** a release with the moving page and `moveIn.js` on `stable`, rebuilt at the new address; this repository's deploy workflow then publishes the moving page (`npm run build:move`, and with `VITE_CHANNEL=test` into `test/`) at the old address instead of the app. The owner moves their own devices first (their Android tablet's installed app above all), then testers are told, with "What's new". Meanwhile each release also needs the command above.
3. **Once the testers have moved:** the moving page goes; the domain moves from `yutuchinese-site` to this repository (removed there, set here: a few minutes without the site while the certificate comes), whose workflow builds `app/`, `app/test/` and the page at the top as `site-repo/deploy.yml` does; `yutuchinese-site` and `hanzi-trainer` are deleted; GitHub then forwards anything under the old address to the new by itself. Deploys are automatic on push again.

**DNS** (Cloudflare, 2026-11-10, all "DNS only"): `yutuchinese.com` A 185.199.108.153, .109.153, .110.153, .111.153 and AAAA 2606:50c0:8000::153 to 8003::153 (GitHub Pages' addresses, from GitHub's documentation, checked against `bunnyapocalypse.github.io`); `www` CNAME `bunnyapocalypse.github.io`; GitHub's TXT `_github-pages-challenge-bunnyapocalypse` (the domain verified for the account, so no one else's Pages site can claim it); `sync` A and AAAA to the sync server. Never a wildcard record (GitHub: a takeover risk even when verified). Proton Mail's records are there too.

**The default Android icon** (the owner's tablet, 2026-11-10): the app added to the home screen from `yutuchinese.com/app/` in Firefox got Android's default icon, the right name; the manifest and icons were right, giving the root page the icon and manifest too (`site-repo/deploy.yml`) and clearing Firefox's cached images didn't help, **restarting the tablet did** (the launcher keeps its own icons). Say so to a tester who sees it. (Firefox on Android makes a shortcut rather than installing from the manifest, and its icon is known to be unreliable: Mozilla bug 1234558.)

**The site's root** at the switch-over: a page forwarding everyone to `app/` at once (in the browser: GitHub Pages has no server redirects; nothing the browser keeps, so a front page replaces it later without leftovers).
