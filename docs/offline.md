# Offline use and deployment

The owner chose (2026-10-13): all stroke data saved on the device, and automatic deployment.

## The two copies

- **Two copies at one site** (the owner, 2026-10-13). `.github/workflows/deploy.yml` builds both, from their branches, whenever `main` is pushed or the workflow is started by hand (after `npm test` on each; not the browser tests). A push to `main` changing only `docs/` or Markdown files starts nothing (`paths-ignore`, 2026-11-10): each run sends the whole site again. Pages usually puts the files in place (about 350 MB uploaded) in under a minute, but now and then hangs at "syncing_files" until `deploy-pages` gives up after 10 minutes ("Timeout reached"; it allows no longer): start a fresh run. On 2026-11-10 it hung four times in a row, with no incident on GitHub's status page.
  - **stable**, from the `stable` branch, at https://bunnyapocalypse.github.io/yutu-chinese/: what people use, the owner's data included;
  - **test**, from `main`, at `.../yutu-chinese/test/`: live within minutes of a push to `main`.
- **To release** (ask the owner first): the entry at the top of `src/changes.js`, then `git push origin main:stable` and, after it, `git push origin main`: the run started by the push to `main` builds the new `stable` with it, one run for both (2026-11-10; two runs at once, as before, competed and timed out). Only if `main` had nothing new to push (or the push changed only notes), start a run by hand: `gh workflow run deploy.yml --ref main`. The push to `stable` starts nothing by itself: the `github-pages` environment only lets `main` publish (a run from `stable` is refused, "not allowed to deploy due to environment protection rules"). If it fails with "Fetching artifact metadata failed", start a fresh run; a re-run uploads a second copy and fails.
- **The test copy is told apart by `VITE_CHANNEL=test`** (`__CHANNEL__`, `vite.config.js`). A browser keeps one set of databases and caches for the whole site, so the test copy has its own database (`hanzi-trainer-test`, `src/db.js`) and app-file store (`test-app-…`), and the stable service worker leaves `test/` alone. It says "(test)" in its title, version line and home-screen name, and has no recording packs (to stay under GitHub's 1 GB; the two copies are about 565 MB). **Anything else kept per site must be kept apart the same way.**
- **The build is relative** (`base: './'`), so `dist/` works in any folder; build addresses with `import.meta.env.BASE_URL`, never a leading `/`.

## The service worker and offline data

- **`src/serviceWorker.js`** is copied by `scripts/build-offline.js` (`postbuild`) to `dist/sw.js` with `VERSION` (a fingerprint of the app's files) and `APP_FILES` in front. It answers from the device's caches if it can, the network otherwise. None under `npm run dev`.
- **The recordings of "Basics of Chinese" are app files** (`BASICS_RECORDINGS` in `src/basicsSounds.js`, 11 small files; 2026-10-21), so that page plays offline from the start; every other recording is kept once played or saved from Settings.
- **Two caches:** `app-<VERSION>`, replaced each version; `offline-data` (stroke data, dictionary, word lists, notes), kept across versions. Recordings have their own store (`docs/word-page.md`).
- **Stroke data is saved in the background, in packs**: 10,600 files one by one is too slow for a phone, so they are packed 600 to a file into `dist/offline/` (18 packs, 35 MB; about 14 MB downloaded), listed in `offline/index.json`. `saveOfflineData` in `src/offline.js` puts every file into the cache under its own address, so `loadCharData` and the service worker know nothing of packs. A pack's name carries a fingerprint and a finished pack leaves a mark, so an interrupted download resumes and unchanged packs aren't fetched again. The single files stay in `dist/` until the packs are in.
- **A new version waits** for "New version ready: tap to reload" in the footer, so the app never changes under a review; without the tap it takes over once every window of the app is closed.
- **Long-term storage** (`navigator.storage.persist()`) is asked for in the introduction or from Settings, never by itself (`docs/interface.md`); Settings shows how it stands under "Offline use", with the download's progress.
- **`tests/browser/offline.browser.js`** builds the app, serves `dist/` from a sub-folder with a plain file server (`startBuiltApp`, like GitHub Pages), waits for everything to be saved, fakes a new version, stops the server and checks writing, the dictionary and tone cards. It leaves `dist/` built.
- **Not tested here:** installing on a real phone, and airplane mode on it.

## The old address

The repository was renamed from `hanzi-trainer` to `yutu-chinese` on 2026-10-15, moving the site. GitHub forwards a renamed repository's code and remotes but not its Pages site, so:

- **Words and progress came along by themselves** (data is kept per site, not per folder); possibly not in an app on an iPhone's home screen, untested.
- **A new repository `BunnyApocalypse/hanzi-trainer`** publishes only `redirect/` (see its README): a page, also as `404.html`, sending any address under `/hanzi-trainer/` to the same place under `/yutu-chinese/`, and a `sw.js` (also `test/sw.js`) that replaces the old service workers, removes itself and sends open windows on, since an installed copy never asks for the page but does check `sw.js`. ## The move to yutuchinese.com

**Decided by the owner (2026-11-10):** the app moves to its own domain, `yutuchinese.com` (bought on Namecheap, DNS at Cloudflare), still on GitHub Pages: the stable copy at `https://yutuchinese.com/app/`, the test copy at `/app/test/` (the same layout as `/yutu-chinese/` and `/yutu-chinese/test/`, so the service worker and packs work unchanged). The site's root is kept for a page about the app, to come later; until then it forwards to `/app/` (later it can send someone who already uses the app straight in, as Skritter does: same site, so it can tell). `www` forwards to the bare domain (GitHub does it). The old address shows a moving page only, never the old app beside the new one (two copies to study in would drift apart). This repository is renamed `yutuchinese`; a new repository takes the name `yutu-chinese` and publishes the moving page at the old address (`old-address/`), as `hanzi-trainer` does for the address before.

**Why a moving page:** a browser keeps data per site (`bunnyapocalypse.github.io` and `yutuchinese.com` are two), so learners' words stay at the old address until handed over; only a page there can read them. GitHub's own forwarding for a custom domain would send people away from them.

**The moving page** (`move.html`, `src/move.js`; built by `npm run build:move` with `vite.move.config.js` and `scripts/finish-move.js` into `dist-move/`, the test copy's with `VITE_CHANNEL=test` into `dist-move/test/`; about 1 MB, no stroke data or recordings): it opens the database with the app's own `db.js` (bringing an old one up to date) and, with no words or reviews, sends the visitor to the new address at once. Otherwise it says how many words and reviews are there and offers:

- **"Move my words"** (`moveByWindow`): opens `<new address>#move-in` in a window, in the tap itself (a window opened later is blocked), and hands over with `postMessage`: the new window says `yutu-move-ready`, this one sends `yutu-move-data` (`buildBackup()`, the sync store and outbox from `readSyncState()` in `db.js`, and the language chosen, `savedLanguage()` in `text.js`), the new one reports its saving in parts (`yutu-move-progress`, shown here as "Saving at yutuchinese.com: {saved} of {total} records"; the owner, 2026-11-10, after a slow move of their own history) and answers `yutu-move-done` or `yutu-move-failed`. A minute without a word from it ends the wait ("didn't answer"), each word starting the minute again. In an installed app (`display-mode: standalone`; Android, a computer) "Done" adds to install the app again from the new address and remove the old one. Each side listens only to the other's site and window. The move is noted in `localStorage` (`moved-at`, `moved-at-test`), so a second visit says when; moving again combines.
- **On an iPhone's or iPad's Home Screen** (`navigator.standalone`), where a window opens in Safari, which keeps its words apart: the steps to add the new address to the Home Screen and join with the sync code (shown, with a link) if the device syncs, else with a backup file; then remove the old app.
- **A backup file**, always.

Nothing is deleted at the old address. Its service worker (`src/moveServiceWorker.js`, published as `sw.js`) replaces the app's: an installed app never asks for the page but does check `sw.js`, so it gets this one, which removes itself and reloads open windows onto the moving page. Caches are left (about 50 MB of stroke data and recordings a device; not yet cleaned up).

**The app taking the words in** (`src/moveIn.js`, before `startUp()` in `main.js`): opened with `#move-in` by a window at `__MOVE_FROM__` (`VITE_MOVE_FROM`; in a build `https://bunnyapocalypse.github.io`), it takes the address's `#move-in` out, waits up to a minute for the words under "Loading…" (opened without a window to answer to, `window.opener` empty, it says so instead, with the backup file, and starts nothing: the app would otherwise greet a learner who has words with the introduction; a reload opens it as usual), checks them (`checkBackup`), restores them (`restoreBackup`, saying how far as Import backup does, `import.saving`) or, if words are there already, combines (`mergeBackups`, as Import backup's Combine), puts the syncing records in place unless this address syncs already (`replaceSyncState`; then `sendEverything` if combined), saves the language (`saveLanguage`), answers, and reloads. Syncing so goes on where the old address stopped, unsent changes included, with the same device in the sync. The introduction is not shown: `welcomeDone` came with the settings.

**Tested** in `tests/browser/move.browser.js` (two dev servers, `localhost:5294` as the old address and `127.0.0.1:5293` as the new: a browser keeps two host names apart): no words, sent on at once; opened with `#move-in` and no window behind it, says so and starts on reload; 109 words, the progress shown at the old address, the language and a sync code handed over, kept at the old address, no introduction. It failed with the receiving side switched off, and caught the language saved after "done" (now before); the test of no window behind fails with the earlier `openedToMoveIn`.

**Not known yet: an app installed on Android from the old address.** After the switch-over its service worker brings the moving page into it, but "Move my words" opens the new address outside the app (in Chrome or a browser view of the app's), which may not keep the way back to it; then the new window says so and the backup file is the way (Android's installed apps share Chrome's data, so nothing is lost). The owner tries it on their tablet first after the switch-over; if it fails, the moving page gives installed Android apps the steps the Home Screen gets.

**Switch-over** (one sitting with the owner):

1. `git push origin main:stable` and `main`, with the moving page and `moveIn.js` (a release; the moving page's workflow builds from `stable`).
2. Rename this repository to `yutuchinese` (Settings › General); point remotes at it (`git remote set-url origin git@github.com:BunnyApocalypse/yutuchinese.git`).
3. Create `BunnyApocalypse/yutu-chinese` (public) from `old-address/`: its README, `deploy.yml` as `.github/workflows/deploy.yml`; Settings › Pages › Source: GitHub Actions; run it (`gh workflow run deploy.yml -R BunnyApocalypse/yutu-chinese`). The old address then shows the moving page.
4. In this repository: the deploy workflow puts the stable copy at `app/`, the test copy at `app/test/`, and a page forwarding to `app/` at the top; Settings › Pages › Custom domain `yutuchinese.com`, then "Enforce HTTPS" once the certificate is there (up to an hour).
5. Links to the repository by its old name: Send feedback's issues (`src/feedback.js`), the credits and the self-hosting link (`src/text/*.js`), `README.md`, the docs, `CLAUDE.md`; "What's new".
6. The owner moves their own devices first; then testers are told.
