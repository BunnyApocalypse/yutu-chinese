# Browser tests

- **No dependency was added.** The tests start the Chromium installed on the computer (`chromium-browser`, `chromium` or `google-chrome` on the PATH, or `CHROME_PATH`) without a window, and drive it over the DevTools protocol with Node's built-in WebSocket. They start their own Vite dev server on port 5273, so `npm run dev` need not be running.
- **Parallel by sharing a pool of browsers.** `startBrowsers` starts several (half the processor's cores; `BROWSERS=3` to choose), each with its own temporary profile and so its own IndexedDB. A test asks the pool for a page with `browsers.use(...)` and gets whichever is free. Node's test runner runs as many tests at once as there are browsers (`concurrency` on the `describe`).
- **As many at once as free memory allows** (`tests/browser/run.js`, which `npm run test:browser` runs; the owner, 2026-10-15, after a run filled a 15 GB laptop's memory and brought the session down). Before, Node ran up to one file fewer than the cores at once, each file with its own Vite server and browser, and the writing grid with half the cores' browsers. Now the runner counts 400 MB per browser with its server (about 300 measured), uses half the memory free at the start, and prints what it chose: half the browsers that fit go to files at once (`--test-concurrency`), the rest to the grid (`BROWSERS`). `TEST_FILES=2 BROWSERS=3` set them by hand; file names after `npm run test:browser --` run only those. On the laptop with 5.6 GB free: 4 files at once, 4 grid browsers, 2.6 GB used. **The writing grid runs as a process of its own beside the other files** (2026-11-05): Node starts test files in order of their names whatever order they are given in, so it began near the end and ran alone, 6 of a run's 8 minutes. Its report is printed at the end. A full run: about four minutes, the grid the last to finish.
- **The test browsers keep everything inside the project** (the owner, 2026-10-19: nothing in `~/Downloads` or elsewhere): each has a folder in `local/test-browsers/` with its profile and the files the app saves (`Page.setDownloadBehavior`), removed when it stops.
- **The test browsers are started with their sound off** (`--mute-audio` in the harness), or the words the tests make the app speak are heard on the computer.
- **`npm test` does not run them:** it only picks up files named `*.test.js`. Browser test files are named `*.browser.js`.
- **Run part of the grid** with `CHARS=學母 npm run test:browser`.
- **Each test draws the same strokes every time**, whichever browser it lands on: its random shaking is seeded from the test's name.
- **Knowing when the next stroke can be drawn:** `src/quiz.js` puts a `data-busy` attribute on the writing area while Hanzi Writer is being handed stroke data (`setBusy`). A stroke drawn then would be lost. The tests wait for the status line to change and for `data-busy` to go, instead of pausing a fixed time. Any new place in `quiz.js` that awaits `giveWriter` must be wrapped the same way; so is the quiz's restart after a long hold (gestures).
- **A stroke that begins outside the writing area never reaches the app**, so the grid skips a character at a position where that would happen (wide characters in "shifted left").
- **Mouse events arrive about 60 a second in headless Chromium**, which is what a run's time is made of. More browsers help; shorter waits do not.
- **A pop-up the page puts up (`window.confirm`) stops everything** until it is answered, and a test's `window.confirm = () => true` is lost when the page is reloaded. Set it again after `reloadApp`.
- **No known failures since 2026-10-13:** all 375 runs of the grid pass (21 skipped; 2026-11-08). **The stroke orders are written at all 6 positions, the other ways** (second shapes, 艹 in three strokes, second forms, the box of 骨) **only centered and small, top left** (0.6 of the size; the two half-size positions went on 2026-11-08, when half the size stopped being followed) (`FEWER_POSITIONS`, 2026-11-05: at every position the grid had grown to 590 runs). The command exits with an error if any fail.
- **Failing now and then** (seen 2026-10-20): `offline.browser.js`'s "starts and works with the server gone". Found 2026-11-04: it stopped waiting at "Saving recordings: 92%", shown while the app looks through what is saved after a reload; it now waits for "All recordings are saved too". **Wait for the end state, not for the first text that mentions it**; likewise, after the app starts again, wait for `main` to lose `starting`, not for text filled early (the five-taps test). **`streak.browser.js`'s "Waited in vain for: the grades"** (2 full runs of 3 on 2026-10-26): it tapped the answer of the card graded before, still up until the next card came, so nothing happened; now it waits for a card asking (`gradeMeaningCard`). Two full runs passed after. **Wait for the next card itself, not for any text on the face.** **`offline.browser.js`'s five-taps test, "Waited in vain for: the group For testing"** (full runs only, 2026-11-05 and 06): it tapped while the built app was still unpacking the stroke data and dictionary into the cache (`saveOfflineData`), which keeps the page busy for seconds, so the taps were answered late; with the browser slowed 6 times (`Emulation.setCPUThrottlingRate`) the group took up to 2 s and once over 5 s. It now waits for "saved too" first, before the taps and again after the app starts again (`waitForOfflineData`): 6 to 44 ms when slowed. **A test of a built app waits for the unpacking to finish before timing anything.**
- **In a git worktree** (`.claude/worktrees/…`, 2026-11-08): `node_modules` is a link to the main copy's, outside the project, and Vite refused sql.js's `.wasm`, so every Anki test failed there and nowhere else; `vite.config.js` now allows its real folder (`server.fs.allow`). The fifth Anki test then waited forever on a database transaction that had ended in an error, which held the whole run up for good: **a promise in a page that waits for a transaction must also end on `onabort`**.
- **Grading in Review** is in `review.browser.js` (since 2026-10-17): the suggested grade (Good, Hard after a mistake or a hint, Again for a missed character), what a grade saves, a meaning card, the hint setting and Card types; since 2026-10-21 "missed" and "right" between characters, and going back to correct a grade. Its cards are put straight into the database; a card graded holds back its word's other cards for a few minutes (`SIBLING_GAP_MS`), so `makeDue` puts every card's last review long ago.
- **Settings covered** (2026-10-17): every control is touched by some test, except Install, Keep data (both need a real browser's answer) and Import's button (`merge.browser.js` uses its file box). Raw input and saving a backup are in `settings.browser.js`; a backup file is caught by replacing `URL.createObjectURL` and a link's `click` in the page.
- **Not covered yet:** drawing a tone mark on a tone card (tone buttons are covered). Use the same harness.
- **Wait for a button to be shown before tapping it, not for something shown before it.** The offline test tapped "Save all recordings" as soon as the line about recordings appeared; the app attaches the button's listener a moment later (after one more `await`), and shows the button then. With the computer busy, the tap came first and did nothing: that was why the offline tests failed now and then in a full run only (found on 2026-10-17 by adding a 500 ms pause there, which made it fail every time, alone). A tap on a hidden button reaches it all the same (`tap` calls `click()`), so nothing else gives this away.
- **A tap on the card is a whole touch** (since 2026-10-24): send `pointerdown` then `pointerup`, both with `isPrimary: true`. A tap that moves on counts only if its finger came down after the step ended (`src/freshTap.js`), so a lone `pointerup` does nothing there.
- **Text in a hidden part reads as empty** (`textOf` in the harness): since 2026-10-16 Settings shows one group at a time (`openSettings(page, group)`) and the forms for adding to a deck are tabs of a panel (`useAddForm(page, form)`, the panel left closed).
- **A setting is saved before it takes effect** (`change` in `src/settings.js` awaits the database), so after `choose(...)` a test waits for the effect instead of checking at once.
- **Speaking to a worker:** `page.send(method, params, sessionId)` and `page.on(method, handler)` (2026-11-07), for a worker's own session after `Target.setAutoAttach` with `flatten`. DevTools' CPU slowing works only on pages, not workers; to slow a worker too, run the whole thing under Linux's CPU limit (`systemd-run --user --scope -p CPUQuota=30% node …`, about 6x), never Chromium alone inside a wrapper (the harness then stops the wrapper but not the browser).
- **Each test file starts its own server and browsers**, and Node runs the files side by side. A file whose steps build on each other (`words.browser.js`) uses one browser and `concurrency: false`.
